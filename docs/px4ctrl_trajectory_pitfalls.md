# px4ctrl 轨迹控制调试踩坑记录与原理解析

本文档记录了基于 `px4ctrl` (或类似 Fast-Planner/Ego-Planner 底层) 进行无人机自定义轨迹规划（如画圆轨迹）时极易触发的炸机坑点，以及相应的解决方案和控制原理科普。

## 1. Z轴高度突变 (Position Step)
* **表现**：无人机在较高处挂机（如 10m 悬停），运行规划脚本瞬间直接剧烈俯冲坠机。
* **原因**：脚本中硬编码了巡航高度（如 `z = 1.0`）。当目标突然从 10m 变为 1.0m，位置误差瞬间达到 9m。
* **原理解析 (Geometric Control)**：如 `px4ctrl` 的几何控制器极其依赖位置误差产生的修正力。9m 的高度落差会使得控制器瞬间下达极端的下行加速度和推力指令，电机大面积怠速或受力不均，导致无人机瞬间失稳。
* **解决方案**：在启动脚本时动态读取当下的 Odom `(x, y, z)`，将起始实际 Z 轴高度作为设定的安全飞行高度。

## 2. 状态突变：速度、加速度与偏航角断层式跃变
* **表现**：修改高度后重新起飞，脚本接通瞬间机体疯狂横滚并丢失姿态。
* **原因**：从 $v=0, a=0$ 的悬停状态，在 $t=0$ 的瞬间直接发送 $v=0.83 m/s$ 以及 90 度目标偏航角 (Yaw)。
* **原理解析 (Feedforward and Smoothening)**：
  * **前馈控制**：`px4ctrl` 依赖前馈速度和加速度计算无人机的推力倾角。若初速度和加速度突变，相当于在空中受到猛烈“踹击”。
  * **姿态调优**：瞬间 90 度的机头调转要求会让底层控制器产生巨大的扭矩请求，非常容易让姿态角解算器超出阈值发生翻转。对于正规框架如 `kr_trackers`，一定是遵循“最小加加速度 (Minimum Jerk)”等原则来生成多项式平滑插值曲线。
* **解决方案**：引入简单的**状态机切换**机制：
  1. `YAW_ALIGN`（偏航对齐状态）：原地保持 $v=0, a=0$，花费数秒平滑旋转机头。
  2. `TRACKING`（起步加速状态）：利用半个周期的余弦曲线，花几秒钟将角速度和线速度从 0 缓坡爬升到设定值，最后再进入匀速画圆。

## 3. 消息标志位 (Flag / ID) 缺失导致机体坐标系误判（最隐蔽的坑）
* **表现**：前两者修复后，脚本运行大约 1~2 秒，控制端报 `[px4ctrl] VEL_IN_BODY!!!` 和 `Attitude failure (roll)`，飞机抽搐侧翻触发 Failsafe。
* **原因**：发送的 `PositionCommand` 消息中，未给 `trajectory_id` 和 `trajectory_flag` 赋值（默认为 0）。
* **原理解析 (State Machine & Frame ID)**：
  * `trajectory_id` 为 0 通常代表空包或失效包。如果不更新 ID，控制器会判断该轨迹过期或者无效。
  * `trajectory_flag` 决定了控制器内部如何解读速度、加速度等数据所在的坐标系（如 世界坐标系 World Frame 还是 机体坐标系 Body Frame）。当 Flag 为 `0` 时，触发了 `px4ctrl` 的防错机制，误把世界坐标系的速度当作机体坐标系处理 (`VEL_IN_BODY`)。仅用 0.5 秒钟，解算出的滚转倾角 (Roll) 就会堆积至极限，使得系统判定姿态崩溃。
* **解决方案**：发包前务必填入规范的 Flag：
  ```python
  cmd.trajectory_id = 1
  cmd.trajectory_flag = 1  # 或对应 msg 内宏定义 TRAJECTORY_STATUS_READY
  ```

## 总结
使用 `px4ctrl` / `PositionCommand` 接口进行开发时，必须遵守三个硬性要求：
1. **平滑第一**：控制变量 $(p, v, a, j, \text{yaw}, \text{yaw\_dot})$ 必须严格连续可导，严禁阶跃。
2. **读懂当前状态**：动作的初始态 $p_0$ 必须与机体现有状态完全匹配。
3. **补全协议约束**：ID 与 状态标志位 Flag 是底层状态机安全流转的“门票”。
